## 一、与产品计划书的三处必要偏差（产品承诺 vs Android 现实）

这三点必须在动手前明确，否则会做出"看起来对、但核心承诺是假的"的产品。

### 1. `createTrashRequest` **不释放空间** —— 最大冲突

计划书 §3.4 的「已释放 58 MB」和结算页的「释放空间」在 Android 上**不成立**：移入系统回收站只是把 `IS_TRASHED` 置 1，字节要等系统 ~7 天后过期或用户清空回收站才真正回收。

**处理方式**（保留计划书 §3.3「永不立即删除」的安全设计，同时让数字变成真的）：
- 结算页确认按钮 = 移入系统回收站（安全默认）。
- 文案：确认前「**预计释放**」，确认后「**已移入回收站**」。
- 回收站页新增「**彻底删除**」= `MediaStore.createDeleteRequest()`，**这一步才真正释放空间**，且有自己的系统确认框。
- 只有经「彻底删除」的字节才允许显示「已释放」。
- 每 20 张的中场激励文案：「已标记删除 N 张 · 约 X MB」（不再说"已释放"）。

### 2.「App 内回收站保留 7 天」是系统行为，不是我们的设置

无法设置系统回收站的保留期。7 天正好是 Android 系统回收站的默认过期时间 —— 这句文案是对的，但它是**描述系统**，不是可调项。

**处理方式**：回收站建模为**一个页面、两个阶段**：
- **阶段一（结算前）**：App 内待删队列，零系统介入，撤销即时可用，磁盘无任何改动。
- **阶段二（结算后）**：系统回收站，用 `QUERY_ARG_MATCH_TRASHED + MATCH_ONLY` 列出，`createTrashRequest(..., false)` 恢复。

因此 P1 设置里的「**回收站保留天数**」**删除**（做一个不起作用的滑块比不做更糟），替换为真实可控项：音效开关、震动开关、默认排序（最近优先/最旧优先）、启动时恢复上次未完成的清理。

### 3.「左滑进入 App 回收站」在进程被杀时有体验漏洞

用户左滑 200 张后退出，照片其实**一张都没动**（安全），但用户以为删了 200 张，重开 App 却什么都不剩 —— 感知上就是"操作丢了"。

**处理方式**（必需，非可选）：持久化会话（范围 + 待删队列）。重开且队列非空时，在范围页顶部显示横幅「上次有 N 张待删除」+「继续处理」/「全部撤销」。

## 四、关键技术设计

### 4.1 滑卡堆（产品核心，风险最高，优先做）

`SwipeCardStackView extends FrameLayout`，内部持**4 张卡片的轮转缓冲**（`cards[0]` 是顶卡），手势交给 `androidx.customview.widget.ViewDragHelper`。

**为什么是 4 张轮转缓冲而不是 1 个复用节点**：Compose 方案里顶卡子树被后续卡片复用，必须靠"飞出→吸附归零→index++"的精细顺序才不会让下一张凭空出现在半空。View 体系里用轮转缓冲天然绕开这个问题 —— 飞出后把该 View 移到缓冲末尾，此时它已在屏幕外**且被其他 3 张盖住**，把它的位移归零是**不可见的**。同时因为它保留着自己的 View 实例，撤销时可以直接把它从原位弹回来，不需要额外的"幽灵卡片"。

**核心机制**：

- **后排卡片的旋转必须确定性派生，绝不在布局期调 `Random`**（否则每次 `onLayout` 都会抖动，且撤销回来时角度会变）：
  ```kotlin
  fun peekRotation(item: PhotoItem): Float {
      val h = (item.id * 2654435761L) xor (item.volumeName.hashCode().toLong() * 40503L)
      return ((h ushr 8) and 0xFFF) / 4095f * 10f - 5f   // 稳定落在 [-5°, +5°]
  }
  ```
  后排缩放递减 `scale = 1 - i*0.04`，`translationY = -(i * 8dp + h*(1-scale)/2)`。
  > 第二项是居中缩放把顶边推下去的高度（`h` 为卡片高）。两项相减后正好是「每层上露 8dp」，
  > 与设计图 01 的三张卡顶边 228 / 220 / 212 逐像素对上。**后排是向上露出的，不是向下。**
  > 另外缩放步长写死在 `SwipeCardStackView.SCALE_STEP`，**不能放进 `dimens.xml`**（理由见 进度.md「已知风险」）。

- **ViewDragHelper 移动 layout 位置（left/top），旋转与印章透明度由 `dx/dy` 派生**。这是 ViewDragHelper 的标准用法（DrawerLayout / SlidingPaneLayout 同款）。`ViewGroup.offsetLeftAndRight` 只做偏移 + `invalidate`，**不触发 measure/layout 重跑**，所以不会和 `onLayout` 打架。`onLayout` 必须在拖拽进行中跳过顶卡（用 `isDragging` 标志守卫），否则一帧抖动会把卡片弹回原位。

- **释放时把 layout 偏移换算成 translation，再开始动画**（View 体系里最容易写出"跳一下"的地方）：
  ```kotlin
  view.translationX += dx;  view.offsetLeftAndRight(-dx)
  view.translationY += dy;  view.offsetTopAndBottom(-dy)
  ```
  视觉位置完全不变，但从此所有动画代码只操作 translation 空间，不再混用 layout 位置与 translation 两套坐标系。

- **抛飞用真抛物线**：`ObjectAnimator.ofPropertyValuesHolder` + `PropertyValuesHolder.ofKeyframe(View.TRANSLATION_X / TRANSLATION_Y, ...)`，`duration = 280ms`，中点（140ms 处）向上拉 `-40dp` 复刻设计图的"先抛起再落下"；`rotationZ` 继续跟随位移。

- **回弹用 `SpringAnimation`**（`androidx.dynamicanimation`，这正是 Compose `spring()` 的 View 版原型）：
  ```kotlin
  SpringAnimation(view, DynamicAnimation.TRANSLATION_X)
      .setSpring(SpringForce(0f).apply { dampingRatio = 0.72f; stiffness = SpringForce.STIFFNESS_LOW })
      .start()
  ```
  x / y 各一个，独立运行。**注意三个已踩的坑**：①`SpringForce` 只有
  `STIFFNESS_HIGH/MEDIUM/LOW/VERY_LOW` 四档，**没有 `STIFFNESS_MEDIUM_LOW`**；
  ②不必 `setStartValue`，不设时它自动取属性当前值；
  ③`addEndListener` 的回调是 **4 个参数** `(animation, canceled, value, velocity)`。

- **阈值**：`|dx| > 0.25 * width`，或 `|vx|` 超过抛掷速度且方向与位移一致（`vx` 从 ViewDragHelper 的 `onViewReleased` 拿到，不用自己写 `VelocityTracker` —— 这是选 ViewDragHelper 的主要收益）。

- **撤销飞回**：history 每项记录 `(item, decision, exitX, exitY)`。`undo()` 时缓冲轮转回退，**先把该 View 的 translation 设回记录的 exit 点**（此刻它在屏幕外，不可见），再 `SpringAnimation` 归零。因为动画只作用在 translation、layout 位置始终稳定，不需要任何覆盖层。

- **输入锁**：`isDragging` 与 `isAnimating` 两个标志，必须**同时**卡住拖拽起点和三个控制按钮。否则 280ms 抛飞期间的快速双击会打乱状态。

- **印章与遮罩**（在 `PhotoCardView` 内）：一个 22% 同色的遮罩 `View` + 一个印章容器（圆角 12dp、4dp 描边、42sp/800 文字、自身 `rotationZ = ±6°`，删除左倾/保留右倾）。`progress = dx / throwThreshold` 的**符号**决定红「删除」/ 绿「保留」（切换文字、颜色、描边、遮罩色）。
  **alpha 要用 `|p| * (0.35 + 0.65*|p|)`，不是 `0.35 + 0.65*|p|`** —— 后者在 `p = 0`（手指刚碰到、
  还没滑）时会留下一个 0.35 alpha 的印章，而设计图 01 的静止态是干净的。乘一个 `|p|` 就同时满足
  「静止为 0」与「滑到底为 1」，且中间段单调。22% 直接编进遮罩色值（`scrim_delete` / `scrim_keep`），
  View 的 alpha 专心当驱动量。直接改 `view.alpha`，不走 `graphicsLayer`。

- **上滑「待定」**：按计划书做「上滑=暂不确定」，但加严格闸门 `dy < -0.35*height && |dy| > 2*|dx|`，避免水平滑动误触。stage 4 在真机上验证手感，若仍误触就退回控制行按钮形式（计划书自己写了"手势不冲突才加"）。

- **对外接口**（阶段 3 实际落地的版本）：
  ```kotlin
  class SwipeCardStackView : FrameLayout {
      class CardDeps(uriOf: (PhotoItem) -> Uri, imageLoader: ImageLoader, soundPlayer: SoundPlayer)

      // startIndex：视图重建后回到之前的进度，别让用户从头再滑一遍
  ```

  > 与初稿的差异：①`bind` 多一个 `startIndex`（转屏后接上进度）；
  > ②依赖（uri/ImageLoader/SoundPlayer）凑成 `CardDeps` 传进来 —— 卡片堆自己拼不出 URI
  > （`domain/` 不持 `Uri`），音效也只在它这一层才知道「什么时候该响」；
  > ③去掉了 `onDragProgress`：提示与氛围在阶段 3 没有用到，等阶段 4 真需要再加，

  进度条、`← 左滑删除` / `右滑保留 →` 提示、三个控制按钮都在 **Fragment 的布局**里，不在卡片 View 内。

### 4.2 MediaStore 层

**必须按 volume 建 URI**：`_ID` 只在单个 volume 内唯一。用 `MediaStore.getExternalVolumeNames(context)` 枚举，逐 volume 建 `Images.Media.getContentUri(volume)`，item URI 用 `ContentUris.withAppendedId(collection, id)`。全 App 内身份是 **`(volumeName, id)`** 而非 `id`。`EXTERNAL_CONTENT_URI` 可用于查询（合成视图），但写回前必须换回所属 volume —— SD 卡上的照片移入回收站失败，就是踩了这一点。

**Projection**：`_ID, VOLUME_NAME, DISPLAY_NAME, SIZE, DATE_TAKEN, DATE_ADDED, DATE_MODIFIED, MIME_TYPE, WIDTH, HEIGHT, IS_TRASHED`

**时间戳陷阱（一定会踩）**：`DATE_TAKEN` 对大量真实照片为 **null**（OEM 截图、下载、微信保存图都有），而 `DATE_ADDED` / `DATE_MODIFIED` 单位是**秒**、`DATE_TAKEN` 是**毫秒**。在**唯一一处**（`PhotoItem.from(cursor)`）归一化：

```kotlin
val takenAt = dateTaken ?: dateAdded?.times(1000) ?: dateModified?.times(1000) ?: 0L
```

并且**不要在 SQL 里按 `DATE_TAKEN` 排序**（各 provider 对 null 的排序行为不一致），一律在 Kotlin 侧按归一化后的值排序。这个函数要配 null 场景的单测。

**范围与查询策略**：

| 范围 | 查询 |
|---|---|
| `AllPhotos(NEWEST_FIRST / OLDEST_FIRST)` | 一次全量扫描，Kotlin `sortedByDescending/By { takenAt }`（反向只是 reverse，不重查） |
| `ByMonth(YearMonth)` | 同一份列表在 Kotlin 侧 `groupBy` 出月份桶 |

**月份过滤放在 Kotlin 而不是 SQL**：一次扫描同时产出范围页需要的每月张数、体积、以及 `2024 年 4 月 · 298 张` 副标题，还彻底绕开 null `DATE_TAKEN` 的 SQL 问题。无时间戳的行归入「未知日期」桶而不是消失。

**分页：不要**。只物化**元数据**（1 万行 × 几个字段 ≈ 1MB，5 万行也还好），位图由 Coil 的有界 LRU 管。Paging 解决的是不存在的问题，还会引入与"按 index 取卡片"设计相冲突的异步模型。真有 10 万张的库再说。

**新鲜度**：每个 volume `registerContentObserver(collection, true, observer)` 并重新发射。结算确认后系统已改动 `IS_TRASHED`，缓存必须失效 —— 滑卡页、结算统计、回收站页都读这条 Flow。Observer 的生命周期挂在 `AppContainer` scope 上，不要挂 Fragment。

**缩略图**：Coil 2.7.0 默认对 `content://media/...` 会**解码原图并降采样**，不走 `loadThumbnail`。设计图明确说"相册性能敏感"，目标机型是小米 10 + 千张级库 —— 所以**一开始就写 `ThumbnailFetcher`**（`ContentResolver.loadThumbnail(uri, Size(w,h), null)`，已验证 API 29+ 可用），通过 Coil 的 `Fetcher` / `ImageLoader.Builder.components { add(...) }` 接入。这比事后优化便宜。

尺寸：顶卡请求 `Size(720, 960)`，后卡 `Size(360, 480)`。**关闭 crossfade**（刚浮出的卡片做淡入会被读成闪烁）。每次滑动后 `imageLoader.enqueue` 预载后面 2 张，把解码挪出关键帧。

> **阶段 3 实测后修正：`ThumbnailFetcher` 不能无条件接管。** `ContentResolver.loadThumbnail`
> **无视请求的 `Size`**，MIUI 上一律返回**源图的 1/4**（1080×2340 的截图 → 270×585）。
> 好处是快 5 倍、省 7 倍内存；坏处是贴到 759px 宽的卡片上是 2.8 倍放大，明显发虚。
> 所以最终做法是**角色感知**：只有**后排卡**的请求带上
> `ThumbnailFetcher.PARAM_USE_PROVIDER_THUMBNAIL` 走 `loadThumbnail`，
> **顶卡不带**，退回 Coil 默认（解码原图再降采样，实测 `720×960 → 720×1560`、~180ms、~4.5MB）。
> 顶卡那 180ms 由「预载后面 2 张」的机制提前吃掉 —— 注意**预载要用顶卡尺寸**，
> 这样卡片升为顶卡时命中的是内存缓存，否则会看到一次「糊 → 清晰」的替换。
> 完整数据见 进度.md「四、开放项 #6」。

### 4.3 权限与引导

**Manifest**：
```xml
<uses-permission android:name="android.permission.READ_EXTERNAL_STORAGE" android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES" />
<uses-permission android:name="android.permission.READ_MEDIA_VISUAL_USER_SELECTED" />
```
不需要 `WRITE_EXTERNAL_STORAGE`（`createTrashRequest` 靠用户逐次授权，不需要写权限），不需要 `VIBRATE`（用 `performHapticFeedback`）。**不**声明 `MANAGE_MEDIA`（见 §4.4）。

```kotlin
fun requiredPhotoPermissions(): Array<String> = when {
    Build.VERSION.SDK_INT >= 34 -> arrayOf(READ_MEDIA_IMAGES, READ_MEDIA_VISUAL_USER_SELECTED)
    Build.VERSION.SDK_INT == 33 -> arrayOf(READ_MEDIA_IMAGES)
    else -> arrayOf(READ_EXTERNAL_STORAGE)          // API 30–32
}
```

34+ 两个一起请求，用户才能看到「允许全部」vs「选择照片」的完整对话框；只拿到 `READ_MEDIA_VISUAL_USER_SELECTED` 即 PARTIAL 状态。

**访问级别判定必须用 `ContextCompat` 重新查，不要相信 `registerForActivityResult(RequestMultiplePermissions)` 回调的 map**（OEM 与 34+ 部分授权流程的上报不一致，这是已知陷阱）：

```kotlin
fun accessLevel(ctx: Context): AccessLevel = when {
    granted(READ_MEDIA_IMAGES) -> FULL
    Build.VERSION.SDK_INT >= 34 && granted(READ_MEDIA_VISUAL_USER_SELECTED) -> PARTIAL
    Build.VERSION.SDK_INT < 33 && granted(READ_EXTERNAL_STORAGE) -> FULL
    else -> DENIED
}
```

- **引导页**：用途说明「照片只在本机处理，永不上传」+「允许访问相册」按钮，用 `SettingsStore.onboardingDone` 把关。
- **拒绝页**三个出口：重新授权 / **前往设置**（`Settings.ACTION_APPLICATION_DETAILS_SETTINGS`，包 `try/catch ActivityNotFoundException`）/ 大白话说明。**小米机型把"前往设置"作为主路径而不是兜底**：MIUI 上第一次点"不允许"就可能让 `shouldShowRequestPermissionRationale()` 变成 false，标准的"永久拒绝"判据在 MIUI 上不可靠。
- **PARTIAL 横幅**（34+）：范围页顶部常驻「当前仅可访问你选择的照片 · 重新选择」，重新触发 `READ_MEDIA_VISUAL_USER_SELECTED` 会重开系统选择器。
- **返回时重查**：在 `onResume` 里重新判定（或 `viewLifecycleOwner.lifecycle` 观察 `ON_RESUME`），不能只依赖 `onViewCreated`。

### 4.4 删除 / 回收站架构

**一个真相源：待删集合从历史派生，不单独存储。** 撤销一张 DELETE 就自动从 `pendingDelete` 消失，不存在第二个 store 需要同步。**撤销栈本身就是结算前的回收站**：在用户确认前，没有任何"已删除"状态被持久化。

**持久化选 DataStore 而不是 Room**：
- 载荷是一个同质的、只在启动时读一次的小对象列表 —— 那是**序列化 blob**，不是可查询的表。Room 的价值（索引查询、join、部分更新、迁移）在这里全用不上。
- Room 需要 **KSP**，而 KSP 版本必须与 Kotlin 2.0.21 精确匹配。为一个列表引入注解处理器，是拿主要风险换零收益。
- 序列化用 **`org.json`**（Android 内置，零依赖、零插件）写进一个 `stringPreferencesKey("pending_queue")`，手写 `toJson`/`fromJson` 约 30 行、可单测。**不引入 kotlinx-serialization** —— 导航参数走 Safe Args（基本类型），不需要它。
  > **阶段 5 修正：`org.json` 换成了自定义格式**（`data/prefs/SavedSessionCodec.kt`）。
  > 原因不是格式本身 —— 是「可单测」这一条不成立：JVM 单测里拿到的是 `android.jar` 的
  > **桩**，`JSONObject` 的任何方法都抛 `RuntimeException: Stub!`。要用它就得引
  > `org.json:json` 测试依赖或上 Robolectric，两者都与「`domain/` 能在纯 JVM 上跑」冲突。
  >
  > 换掉之后反而更简单：**载荷里没有任何需要转义的字符**。存下来的只有照片身份
  > （volume 名 + 数字 id），显示名/路径这些真要转义的字段根本不存 —— 因为它们活不过
  > 一次对账（照片可能已被别的 App 删掉，那些字段就是过期信息），恢复时一律从新扫描取真值。
  > 于是 `|` / `,` / `:` 当分隔符是安全的。**顺带把载荷从「整条记录」降到「两个字段」**，
  > 而 DataStore 每次 `edit{}` 都要重写整个文件。
  >
  > 另外**存的是「待删」而不是整条撤销栈**：`KEEP` / `UNDECIDED` 重开 App 之后没有意义
  > （撤销一张保留 = 把那张照片再显示一遍，而它一步都没动过），留着只会让载荷随滑动
  > 张数无限增长。代价是**重开 App 后撤销栈是空的**，恢复来的待删只能整体撤销。
- DataStore 每次 `edit{}` 会重写整个 map，但人类滑卡速度（<3 张/秒）+ 几 KB 载荷可接受 —— 仍然**做合并写**：内存累积，在 `onStop` / 离开页面 / 每 N 张时刷盘，让滑动路径上完全不碰 IO。

**过期项必须处理**：持久化的 URI 可能在结算前失效（被别的 App 删了、或上一轮已进回收站）。**在会话开始时**把队列与一次新扫描做一次对账，丢弃已不存在或已 `IS_TRASHED` 的项。不要逐项做。

> **阶段 5 落地：对账 + 恢复的全部逻辑在 `domain/SavedSession.kt` 的 `restoreSession()`。**
> 它一次性算出三样东西：本次队列（**已标记删除的那些不在里面**）、队列里的起点、
> 对账后仍存在的待删。它必须收**整本相册**而不是本次范围的照片 —— 待删可能来自另一个范围
> （先清了 5 月、再点全部照片），只查本次范围会把它们当成「已经不存在」而全部丢掉。
>
> 存下来的 `index` 是**剔除之前**那个队列里的位置，所以要按同样的条件重新数一遍
> （`full.take(index).count { 不在待删里 }`），不能直接拿来用。

**提交：分块状态机**（`TrashCommitter` 纯逻辑 + Fragment 侧 launcher 桥接）

```kotlin
const val CHUNK = 1000        // 文档上限是 2000（targetSdk 36），留一半余量
sealed interface CommitState {
    data object Idle
    data class Awaiting(val chunkIndex: Int, val total: Int, val sender: IntentSenderRequest)
    data class Partial(val trashed: Int, val remaining: Int, val cancelledAt: Int)
    data class Done(val trashed: Int)
}
```

- **一次 `createTrashRequest` = 一个 `PendingIntent` = 一个系统对话框**，覆盖该次调用里的所有 URI。所以 N 块就是 N 个连续弹窗，这是 API 决定的，躲不开。块数 > 1 时界面要明说：「将分 N 批处理，每批需你确认」。
- **桥接方式（ViewModel 不能自己 launch）**：
  ```kotlin
  private val trashLauncher = registerForActivityResult(
      ActivityResultContracts.StartIntentSenderForResult()
  ) { result -> viewModel.onTrashResult(result.resultCode == Activity.RESULT_OK, result.data) }

  viewModel.commitState.observe(viewLifecycleOwner) { st ->
      (st as? CommitState.Awaiting)?.let { trashLauncher.launch(it.sender) }
  }
  ```
  队列状态放进 `SavedStateHandle`，这样对话框期间的重建/进程回收不丢进度。
- **取消语义（明确决定）**：第 2 块返回 `RESULT_CANCELED` 就**停止整批**，不要继续第 3 块 —— 用户已经叫停了。展示 `Partial(trashed, remaining)` + 「继续处理剩余的 N 张」/「稍后再说」，未提交的余量留在待删 store 里可恢复。
- **`IllegalArgumentException` 保护**：分块后依然 try/catch 包一层 —— 这是上限比文档低时唯一的信号，捕获后把 `CHUNK` 减半重试，而不是在流程最后一屏崩溃。
- **恢复方向**：`createTrashRequest(resolver, uris, false)`。`TrashCommitter` 设计成**方向无关**（`commit(uris, trashed: Boolean)`），因为恢复是否也弹确认框尚未实测，两种结果都能直接落地。

**回收站页**：`MATCH_ONLY` 查询列出（`item_trash.xml`：名称/体积/日期）+「恢复」+「彻底删除」（`createDeleteRequest`，唯一真正释放空间的调用，二次确认）。不要在多次导航之间缓存回收站列表 —— 系统可能已让某些项过期消失。

> **阶段 6 落地修正（4 处）**：
> 1. **`TrashCommitter` 的 `State` 不持 `IntentSenderRequest`**（初稿的 `Awaiting` 里有它）。
>    状态机是纯 Kotlin，只存 `total / chunkSize / committed / from / count` 五个 Int；
>    `IntentSenderRequest` 由 ViewModel 现建，放进 `Channel<Effect>` 交给 Fragment。
>    `SavedStateHandle` 因此只需要存 `committed / chunkSize / done`。
> 2. **`trashed=false`（恢复）也走同一个 launcher**。开放项 #1 到现在仍未实测，
>    但两条路径的调用方式一致，所以「恢复是否弹框」不改变任何代码。
> 3. **提交开始后，结算页的离开目标固定为范围页**（返回键与 CTA 都是）。
>    滑卡页的 ViewModel 还握着整份旧会话，让它重新 `stage()` 会把已进回收站的照片
>    写回待删队列；回范围页会销毁它。这是「已提交的不复活」唯一简单的保证。
> 4. **`PendingDeleteStore` 必须给 DataStore 配 `corruptionHandler`**：默认 null，
>    文件损坏时抛 `CorruptionException`，而三个页面启动时都读它 —— 表现是每次打开都崩。
>    另外 `load()` 要先看内存里 `staged` 的那份（结算页紧跟滑卡页打开，磁盘可能差最后几张），
>    `flush()` 要先写盘再清 `staged`（反过来的窗口会让结算页读到上一版队列）。

**`MANAGE_MEDIA`（Mode B）不做，仅记录**：它能让 N 个弹窗变成一次授权，但属 Google Play 受限权限、需送审，且 API 30 设备永远用不了。MVP 用 Mode A（分块 + 逐块确认），Mode B 作为将来可开关的升级项。

### 4.5 结算统计

`domain/Stats.kt` 纯函数：`computeSettlement(items, decisions) -> SettlementStats`，字段含 `deletedCount/Bytes`、`keptCount/Bytes`、`undecidedCount`、`totalSeen`、`keptFraction`（堆叠条绿色占比）、`monthLabel`。真相源 = 对 DELETE 集合求和 `SIZE`。

> **阶段 5 修正两处签名**：
> 1. 收的是整个 `SwipeSession` 而不是两个列表。待删集合**不是从历史直接派生的** ——
>    它还要算上 `SwipeSession.detachedDeletes`（重开 App 后恢复的上次会话，那些不在撤销栈里）。
>    拆成两个参数传，就给了调用方「传错一对列表」的机会，而算错的是「要删多少张」这种
>    不可逆动作的输入。
> 2. 没有 `monthLabel`。格式化要 `Context.getString`，而 `domain/` 是纯 Kotlin、要能在
>    JVM 上单测。月份名由结算页自己拼（它本来就有 nav args）。

单测三例：混合夹具、全部保留、空列表（空列表不能让 `keptFraction` 除零）。文案按 §1 的偏差处理（「预计释放」/「已移入回收站」）。

**「本月对比」不在 MVP**：设计图 04 的提示条实际写的是「回收站保留 7 天，删除前可随时恢复」—— 是留存说明，不是同比。计划书 §3.4 提的「本月对比」在设计图里不存在。MVP 按设计图做；将来要加，最小实现只是一个 `monthFreedBytes: Map<String, Long>`。

### 4.6 音效与震动

**震动用 `View.performHapticFeedback(int)`，不用 `HapticFeedbackType` 也不用 `VibratorManager`**：它**不需要权限**、自动尊重系统触感开关、且被 view 的 `isHapticFeedbackEnabled` 把关。

| 事件 | 常量 |
|---|---|
| 保留（右滑） | `HapticFeedbackConstants.CONFIRM` |
| 删除（左滑） | `HapticFeedbackConstants.REJECT` |
| 撤销 / 按钮 | `CLOCK_TICK` / `CONTEXT_CLICK` |

**音效先零资源起步**：`ToneGenerator` 的 `TONE_PROP_ACK`（保留）/ `TONE_PROP_NACK`（删除）。构造有几毫秒开销，所以**只建一次**并放在 `AppContainer`（导航到结算页时不能被杀）。stage 8 换成 `res/raw` 里两个 ~2KB 单声道 WAV + `SoundPool`（`USAGE_ASSISTANCE_SONIFICATION`：UI 音、与音乐混音而非压低、尊重静音/震动模式）。

`SoundPlayer` 生命周期挂在 `AppContainer` 上并在进程退出时 release —— **不要放在 Fragment 的 `onDestroyView`**，那会在导航离开的瞬间掐掉声音。

### 4.7 View 体系下的通用约定

- **ViewBinding** 全量使用（`buildFeatures { viewBinding = true }`），`_binding` 在 `onDestroyView` 置空。不用 `findViewById`，不用已废弃的 Kotlin synthetics。
- **Flow 收集**：`viewLifecycleOwner.lifecycleScope.launch { viewLifecycleOwner.repeatOnLifecycle(STARTED) { ... } }`，不要用裸 `lifecycleScope`（会活在 Fragment 视图之外）。
- **ViewModel 作用域**：`SwipeViewModel` 以及跨「范围→滑卡→结算」共享的会话状态用 `by activityViewModels()`；其余页面各自 `by viewModels()`。
- **列表**（月份列表、回收站列表）用 `RecyclerView` + `ListAdapter` + `DiffUtil`。
- **Insets**：`ViewCompat.setOnApplyWindowInsetsListener` + `updatePadding`，底部控制按钮行必须吃 `navigationBars` inset，否则被手势条压住。
- **不做 `res/values-night`**：设计只有浅色一套，配合主题已经是 `Light` 变体。

## 六、验证配方（Windows + bash）

```bash
cd /e/workspace/SwipeKeep/SwipeKeep
export JAVA_HOME="E:/androidstudio/2025/jbr"     # 必须是 Windows 风格路径，JVM 认不出 /e/...
export PATH="$JAVA_HOME/bin:$PATH"
./gradlew :app:assembleDebug
```
（等价且更稳的写法：`./gradlew -Dorg.gradle.java.home="E:/androidstudio/2025/jbr" ...`）

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell pm clear com.lancer.swipekeep      # 从零重测引导流程
adb shell pm grant com.lancer.swipekeep android.permission.READ_MEDIA_IMAGES        # API 33
adb shell pm grant com.lancer.swipekeep android.permission.READ_EXTERNAL_STORAGE    # API 30–32
adb shell dumpsys gfxinfo com.lancer.swipekeep    # 滑卡时看掉帧
```

注意：**API 34+ 的 PARTIAL（部分授权）状态无法用 adb 造出来**，只能走 UI。MVP 验证阶段在小米 10（33）上跳过该项，逻辑仍需实现。

**播种测试照片**（数量要够测分块与进度，时间要跨月才能测月份分组）：

```bash
mkdir -p /tmp/seed && cd /tmp/seed
for i in $(seq 1 300); do
  convert -size $((800+i*7))x$((600+i*3)) xc:"hsl($((i*13%360)),60%,60%)" \
          -pointsize 48 -fill white -annotate +40+80 "SEED $i" seed_$i.jpg
  touch -d "2024-0$((1+i%6))-1$((i%9)) 12:00" seed_$i.jpg
done
adb push /tmp/seed/. /sdcard/Pictures/SwipeKeepSeed/
```

让 MediaProvider 感知：先试 `adb shell am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file:///sdcard/Pictures/SwipeKeepSeed/seed_1.jpg`；**该广播自 API 29 起已废弃，MIUI 上很可能被忽略**。可靠退路是**重启设备**（触发外部存储重扫，慢但一定生效），或先在系统相册里打开一次。**不要用 `content insert` 造 MediaStore 行** —— 会造出没有实际字节的记录，Coil 解码失败，让你误判"缩略图坏了"。

ImageMagick 输出无 EXIF，所以这批文件正好覆盖 `DATE_TAKEN == null → DATE_MODIFIED` 的**回退路径**（真实世界最常见的 case）。想测主路径就用 `exiftool -DateTimeOriginal="2024:03:15 10:00:00"` 写入。

**删除流程的坑**：
- 2000 上限让多块测试不现实（得播种 4000+ 张）。把 `CHUNK` 做成 `const val`，测多弹窗状态机时临时设为 **5**，用 20 张照片就能完整走"多块顺序 / 中途取消 / 部分结果"三条路径。
- **模拟器可能根本不弹系统确认框**（AOSP 的 API 30 镜像不一定带齐 MediaProvider/DocumentsUI 组件）。此时 `createTrashRequest` 会返回 `PendingIntent` 但不弹窗，结果是 `RESULT_CANCELED` 或异常 —— 和"用户点了取消"无法区分。**所以删除流程的验证一定在真机小米 10（API 33）上做**，并在结果回调里把 `resultCode` 与 `data` 打出来。
- 模拟器时钟若与播种的 mtime 差太多，月份分组看起来会是空的。

## 七、编码前需要在真机上实测确认的开放项

这些我**不猜**，在对应阶段实测：

1. **恢复方向 `createTrashRequest(..., false)` 是否也弹确认框、是否同样有 2000 上限** —— 决定回收站页的恢复是即时还是也要分块 launcher。（`TrashCommitter` 已设计成方向无关，两种结果都能落地）
2. **连续多次 `createTrashRequest` 是否会被系统限流/抑制弹窗** —— 若被抑制，第 2..N 块会以用户看不见的方式失败。**stage 6 在真机验证后再定稿多块 UX**。
3. `VOLUME_NAME` 在 API 30 上是否真的被填充。
4. `buildToolsVersion 35.0.0` 能否配合 `compileSdk 36`（AGP 8.11），还是必须装 36.0.0。stage 0 立即暴露。
5. `createTrashRequest` 确实不需要任何权限（预期正确，fresh install + `pm revoke` 一次确认）。
6. Coil 2.7.0 自定义 `Fetcher` 接 `loadThumbnail` 的实际收益 —— 若收益不明显就退回 Coil 默认降采样，删掉 `ThumbnailFetcher`（少一个文件、少一层自定义）。
