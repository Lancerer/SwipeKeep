**开放项 #6 的实测数据**（小米 10 / API 33，同一张 1080×2340 的截图）：

| 路径 | 输出尺寸 | 端到端耗时 | 内存 | 贴到 759px 宽的卡片上 |
|---|---|---|---|---|
| `loadThumbnail` | 270×585 | 30–36ms | ~0.6MB | 2.8 倍放大，**肉眼可见地虚** |
| Coil 默认（解码原图再降采样） | 720×1560 | 160–190ms | ~4.5MB | 1.15 倍，清晰 |

关键：**1/4 是相对源图**的，不是相对请求。所以 4000×3000 的相机原图能拿到 1000×750（够用），
而 1080 宽的截图/微信图只有 270 宽（不够）。用户相册里后两类很常见，所以不能一刀切走缩略图。
混合方案的代价是保留两层缓存；收益是「看得最仔细的那张永远清晰，被盖住的三张几乎不花钱」。
顶卡那 180ms 被 `preloadAhead` 提前一两个身位预热掉了，轮到时命中的是内存缓存。

## 五、已知风险 / 环境坑（跨会话都要记得）

- **MIUI 会拦 `adb install`**，报 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`（需要"USB 安装"权限，adb 改不了）。**绕过方式**（已实测可行）：
  ```bash
  export MSYS_NO_PATHCONV=1     # 否则 Git Bash 把 /data/local/tmp/... 转成 Windows 路径
  adb push app/build/outputs/apk/debug/app-debug.apk /data/local/tmp/sk.apk
  adb shell pm install -r -t /data/local/tmp/sk.apk
  ```
- **bash 里跑 adb 一律先 `export MSYS_NO_PATHCONV=1`**：Git Bash 的路径自动转换会把设备端路径（`/sdcard/...`、`/data/local/tmp/...`）改写成 Windows 路径；`adb pull` 的目标路径也一样要留意（用相对路径最省事）。

- **MIUI 也拦命令行注入事件与改密度**（阶段 1 踩到，影响所有长页面截图的验证方式）：
  ```bash
  adb shell input swipe/tap/keyevent ...   # SecurityException: 需要 INJECT_EVENTS
  adb shell wm density ...                 # SecurityException: 需要 WRITE_SECURE_SETTINGS
  adb shell pm grant <pkg> <permission>    # SecurityException: 需要 GRANT_RUNTIME_PERMISSIONS
  ```
  三个都改不了（不是权限没给，是 MIUI 直接封了）。**退路**：让页面自己在启动时滚过去 —— 见 `ui/common/DebugScroll.kt`：
  ```bash
  adb shell am start -n com.lancer.swipekeep/.MainActivity --ei scroll 900      # ScrollView，单位是**像素**
  adb shell am start -n com.lancer.swipekeep/.MainActivity --ei scrollPos 12    # RecyclerView，单位是**条目位置**
  ```
  坑：`scroll` 是**像素不是 dp**（小米 10 密度 440，900px ≈ 205dp）；RecyclerView 用**条目位置**才稳定（条目高随内容变）。另外默认 launchMode 下 `am start` 会新建 Activity 实例，所以 `onCreate` 一定拿得到 extra，不用管 `onNewIntent`。
  > **推论（重要）**：本机所有「点一下 / 滑一下」的验证都只能靠人手工做。阶段 2 的排序切换与月份跳转就是这样遗留的。
  > 这意味着凡是「手感 / 交互」类的验收项，都要提前准备一份人工 checklist，不能指望 adb。

- **MIUI 会自动授予媒体权限**：`pm install` 装完后 `dumpsys package` 显示 `READ_MEDIA_IMAGES: granted=true`。所以**不要**把「权限被拒」当成默认起点 —— 想测拒绝态得手动去系统设置里关掉。

- **MIUI 的媒体扫描器会在后台继续索引**，一次会话里相册总数会自己往上走（本次从 1975 涨到 1977）。
  所以「App 计数 vs MediaStore 计数」**必须在同一时刻对比**，隔几分钟的结果不可比 —— 阶段 2 一度因此误判成差一张。

- **`adb shell content query` 的坑（两个，都会静默给错数）**：
  1. **不加 `--where` 时它默认就排除了回收站**，返回的不是「总行数」而是「非回收站行数」。
     拿它当 total 去减 `is_trashed=1` 的数量，会得到「App 少了一张」的错觉（阶段 2 实际踩了）。
     想要的数：`--where is_trashed=1` 显式问回收站；总行数没有直接办法。
  2. **带 `AND` 的复合 `--where` 会被远端 shell 吃掉**，查询条件被静默丢弃 ——
     三个互斥条件会返回**完全相同**的行数（本次都返回 52）。一次只写一个条件。
  3. 列名要小心：`date_taken` 不存在（实际是 `datetaken`，没有下划线）；
     `is_trashed` / `is_pending` / `volume_name` 有下划线。用错列名会报 `Invalid column`。

- **`MutableSharedFlow(replay = 1)` 不会给新订阅者任何东西，如果从来没人发射过。**
  `replay` 重放的是「**已经发射过的**最后一个值」。阶段 2 第一版把变化信号写成
  `MutableSharedFlow<Unit>(replay = 1)` 且只在 `ContentObserver` 回调里 `tryEmit`，
  结果首次进入范围页时 Flow 死活不发射，界面永远停在 `loading` 初始状态 ——
  表现是「列表全空 + 存储卡显示『存储信息暂不可用』」，而权限和查询其实都正常。
  **要「收集即加载」就用 `StateFlow`**（它一定持有当前值）。
  另外 `StateFlow` 会丢弃与当前值**相等**的发射，所以计数器用 `Long` 自增，别用 `Unit`。

- **Coil 2.7 的 `Size.width` 是 `coil.size.Dimension`，不是 `Int`。**
  取像素值要用 Coil 自带的 `size.width.pxOrElse { 兜底值 }`（`coil.size.pxOrElse`），
  自己写 `as? Dimension.Pixels` 是白费劲。`Size.ORIGINAL` 的尺寸是未定义值，
  直接传给 `loadThumbnail` 会抛 `IllegalArgumentException`。

- **`dimens.xml` 里不能放无单位的值**（阶段 3 踩到，崩在构造函数里）：
  ```xml
  <dimen name="x">0.04</dimen>     <!-- AAPT 存成 float，getDimension() 直接抛 -->
  ```
  报错是 `Resources$NotFoundException: Resource ID #0x... type #0x4 is not valid`，
  **type #0x4 = TYPE_FLOAT** —— `getDimension()` 只认 dimension。
  这一步在 `SwipeCardStackView` 的构造里，所以表现是**整个 Fragment 布局 inflate 失败**，
  堆栈最深处的 `Caused by` 指向 `getDimension`，不在 XML 那一层，很容易看错方向。
  无单位倍率（缩放步长之类）就写在 Kotlin 常量里。旧的 `card_stack_scale_step` 已删除。

- **`loadThumbnail` 的输出尺寸由 provider 定，跟请求的 `Size` 无关**（MIUI：源图的 1/4）。
  别指望「请求大一点就拿到大图」。见开放项 #6 的表。

- **`SpringForce` 没有 `STIFFNESS_MEDIUM_LOW`**：档位只有 `HIGH / MEDIUM / LOW / VERY_LOW`。
  `SpringForce` 里也不存在「中等偏低」这个常量（计划书 §4.1 写得不对，已按 LOW 落地）。

- **`DynamicAnimation.OnAnimationEndListener.onAnimationEnd` 是 4 个参数**
  `(animation, canceled, value, velocity)`，不是常见的 2 个。写成 `{ _, _ -> }` 会编译不过。

- **`SpringAnimation(FloatValueHolder)` 可以让弹簧驱动一个裸 float**（阶段 4 用它做「后排露出深度」：
  `androidx.dynamicanimation.animation.FloatValueHolder`，`SpringAnimation(holder)` + `setSpring(...)`，
  `FloatValueHolder` 自带 `getValue()/setValue()`）。用 javap 核实过（`dynamicanimation-1.0.0.aar` 的
  `classes.jar`）。
  **两个坑**：①**这个 holder 本身就是存储**，弹簧的起点是从 `holder.getValue()` 读的
  （不设 `setStartValue` 时），所以不要再另开一个 `var progress` 字段 —— 两份值必然对不上；
  ②**`cancel()` 也会回调结束监听**（`canceled = true`），而 `cancel` 是「新手势接管」的常规动作，
  所以依赖它收尾的地方要自己做幂等保护（阶段 4 的 `Gate`）。

- **本机 SDK 的 `android.jar` 里没有 `android.os.storage.StorageStatsManager`**（`android/os/storage/` 下只有
  `StorageVolume` / `StorageManager`）。所以统计存储用量只能走 `StatFs` + `Environment.getExternalStorageDirectory()`。

- **`JAVA_HOME` 指向 JDK 8**，AGP 8.11 用不了。命令行构建必须 `export JAVA_HOME="E:/androidstudio/2025/jbr"`。**每次新会话都要重新 export**（shell 状态不跨会话保留）。
- **`libs.versions.toml` 里 `lifecycleRuntimeKtx = "2.6.1"` 是既有隐患**：显式版本引用会覆盖 BOM 约束，与 navigation 传递引入的版本冲突，表现为**运行时 `NoSuchMethodError`**，编译期不报错。阶段 0 必须一起修掉。
- **build-tools 只到 35.0.0**，36.0.0 缺失。
- **Coil 不在 Gradle 缓存**，首次构建需联网（其余依赖都已在缓存）。
- **模拟器可能不弹系统删除确认框**，删除流程的验证必须在真机小米 10 上做。
- **Safe Args 里 `long` 的 `defaultValue` 必须带 `L` 后缀**（阶段 5 踩到）：
  ```xml
  <argument android:name="deletedBytes" android:defaultValue="0"  app:argType="long" />  <!-- 构建失败 -->
  <argument android:name="deletedBytes" android:defaultValue="0L" app:argType="long" />  <!-- 对 -->
  ```
  报错是 `generateSafeArgsDebug FAILED: Failed to parse defaultValue '0' as long`。
  `int` / `boolean` / 字符串都不用，只有 `long`（和 `float`，需 `f`）要后缀。

- **卸载重装会让 MIUI 的媒体权限授权失效，而 `pm grant` 补不回来**（阶段 5 踩到，一次就好，
  不值得再踩）：`adb uninstall` + 重装之后 `dumpsys` 显示 `READ_MEDIA_IMAGES: granted=false`，
  而 `pm grant` 照例被 MIUI 拦（`GRANT_RUNTIME_PERMISSIONS`）。
  **能自己长回来的**：重装后第一次进范围页会自动发起请求，MIUI 直接放行（不需要点任何东西），
  但**那一次的列表仍然是空的** —— 扫描在授权之前就跑完了，而 `ContentObserver` 不为「权限变更」
  发信号。所以表现是「第一次进 0 张，退出去再进就 1974 张」。不是 bug，别去查它。

- **DataStore 只读不会创建文件**：`context.pendingStore.data` 读一个不存在的文件时返回
  `emptyPreferences` 而不落盘。所以「`files/datastore/` 目录不存在」**不能**当成
  「存储层没被调用」的证据 —— 阶段 5 一度据此误判。想确认写成功，看 `pm install` 之后
  第一次进滑卡页（会在 `init` 里回写一次），那时文件里有 `v1|A|NEWEST_FIRST|0|` 这样的明文。

- **不要用 Compose 写任何新代码** —— 本工程已确定走传统 XML/View 路线，且会彻底移除 Compose 依赖。

  而它一步都没动过），留着只会让载荷随滑动张数无限增长。**代价说明白：重开 App 后撤销栈是空的**，

### 2026-10-21 — 阶段 6：回收站提交 + 回收站页（代码完成、单测 61 条、请求构造与查询已探针核对；系统框待人工）

**做了**：

- **`data/media/TrashCommitter.kt`（新，纯逻辑）** —— 分块提交状态机 `Idle / Awaiting / Partial / Done`：
  - 状态里只存**偏移量**（`total / chunkSize / committed / from+count`），不存 URI 列表。
    整份队列不必进状态机，`SavedStateHandle` 里只放三个 Int 就能扛过进程回收。
  - `committed` 一定是队列的**连续前缀**（第 3 块没确认就不会开始第 4 块），
    所以「还剩多少」= `total - committed`，不需要记哪些成功哪些失败。
  - **取消 = 停止整批**（`onChunkCancelled` → `Partial`），不会接着弹下一块。
  - `onChunkTooLarge()`：provider 抛 `IllegalArgumentException` 就**块减半重试同一位置**，
    减到 1 张还失败才停 —— 那时已经不是块大小的问题了。
  - `restored()`：进程在系统框期间被杀后，**不自动重弹**（我们不知道那次到底确认了没有），
    恢复成 `Partial` 等用户点「继续」，`cancelledAt = -1` 表示「不是取消、是中断」。
- **`MediaStoreDataSource`**：
  - `loadTrashedPhotos()` 用 `QUERY_ARG_MATCH_TRASHED = MATCH_ONLY`。`mapRows` 的
    「Kotlin 侧再滤一遍 IS_TRASHED」改成开关 —— 回收站查询如果沿用那个兜底，会把要的每一行都丢掉。
  - `createTrashRequest(uris, trashed)` / `createDeleteRequest(uris)` 也收进来：MediaStore 仍然只在这一个文件里。
  - `uriFor(Identity)`：结算页提交的是身份列表，不持整条 `PhotoItem`。
- **结算页加 ViewModel**（`ui/screens/settlement/SettlementViewModel.kt`）：
  - 只管提交，**统计数字仍然走 nav args**（阶段 5 那条「不做 ViewModel」的理由是对统计说的，不是对提交说的）。
  - 系统框必须由 Fragment launch，所以 ViewModel 只把 `IntentSenderRequest` 放进
    `Channel<Effect>` 投递出去。**用 Channel 不用 StateFlow**：同一个 Launch 被订阅两次
    （转屏、回前台）会让系统再弹一次框。
  - `SavedStateHandle` 存 `committed / chunkSize / done`；`pending` 从 store 重新读。
- **取消语义的 UI**：停下时弹「已处理 N 张，还剩 M 张」+「继续处理剩余的 M 张 / 稍后再说」；
  同时把 store 里已提交的前缀剔掉（否则范围页横幅会把已进回收站的那批又报一遍）。
- **`ui/screens/trash/`**：`TrashViewModel`（不缓存，每次进页面/每次操作后重查）、
  `TrashAdapter`（56dp 缩略图走 `loadThumbnail`）、`TrashFragment`
  （恢复 = `createTrashRequest(..., false)`；彻底删除 = 自己一层二次确认 + `createDeleteRequest`）。
- **导航**：nav_graph 加 `trashFragment`；滑卡页顶栏与结算页的「查看回收站」都换成真跳转。
- **`PendingDeleteStore` 三处修正**（都是被这次提交链路逼出来的）：
  1. 加 `corruptionHandler`：文件损坏时默认抛 `CorruptionException`，而范围页/滑卡页/结算页
     **启动时全都要读它** → 表现是每次打开 App 都崩，用户连重置的机会都没有。
  2. `load()` 先看 `staged` 再看磁盘：结算页紧跟着滑卡页打开，那时最后几张可能还没落盘。
  3. `flush()` **先写盘再清 `staged`**：原顺序中间有个「staged 已清、磁盘还没写完」的窗口，
